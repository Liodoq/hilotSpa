## How to test it

Start the app, then in PowerShell:

**1. Register**

```powershell
$body = @{
  firstName = "Test"; lastName = "Customer"
  contact = "09171234567"; address = "Bulan, Sorsogon"
  email = "test@example.com"; password = "hilotspa123"
} | ConvertTo-Json

$auth = Invoke-RestMethod -Uri "http://localhost:8080/api/v1/auth/register" `
        -Method Post -ContentType "application/json" -Body $body
$auth
```

Expect `201` and a response containing `token`, `role: CUSTOMER`, `branchId: null`.

**2. Confirm the wall is up**

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/v1/massages"
```

Expect **401 Unauthorized**. That is the correct answer.

**3. Now with the token**

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/api/v1/massages" `
    -Headers @{ Authorization = "Bearer $($auth.token)" }
```

Expect `[]` — an empty array. Authentication works end to end.

**4. Log in**

```powershell
$login = @{ email = "test@example.com"; password = "hilotspa123" } | ConvertTo-Json
Invoke-RestMethod -Uri "http://localhost:8080/api/v1/auth/login" `
    -Method Post -ContentType "application/json" -Body $login
```

**5. Wrong password**

Change the password in step 4 and re-run. Expect **401**, with the same message as an unknown email.

**6. Look at your token**

Paste `$auth.token` into https://jwt.io. You will see:

```json
{
  "iss": "hilotspa",
  "sub": "<user uuid>",
  "email": "test@example.com",
  "name": "Test Customer",
  "nodeId": "bulan-01",
  "roles": ["CUSTOMER"],
  "exp": 1755500000
}
```

Note what is **not** in there: no password, no hash. A JWT is signed, not encrypted — anyone holding it
can read the payload. So it carries identity, never secrets.

## Four decisions you should be able to defend

**1. Registration cannot create staff or admins.**
`RegisterRequest` has no `role` and no `branchId` field, and `AuthServiceImpl` hardcodes
`Role.CUSTOMER`. The endpoint is unauthenticated, so everything it accepts is attacker-controlled — a
role field there would let anyone POST themselves an ADMIN account. Staff and admin accounts are
created through `/api/v1/users`, which requires a token.

This is the single most common vulnerability in student auth systems. Worth saying out loud at defense.

**2. Login gives the same error for "no such user" and "wrong password."**
Different messages let an attacker enumerate which emails are registered — they submit a list and read
which ones come back "wrong password" instead of "user not found." Both return
`401 Invalid email or password`.

**3. Passwords are hashed at the moment of arrival and never travel back.**
`passwordEncoder.encode()` runs before the entity is saved. `UserModel.password` is write-only —
`UserTransform` never populates it, so it is always null on the way out. `passwordHash` is never
mapped to a model at all.

`DelegatingPasswordEncoder` stores the algorithm inside the hash, so rows look like
`{bcrypt}$2a$10$...`. That means you can migrate to a stronger algorithm later without invalidating
existing passwords — old hashes keep verifying with bcrypt, new ones use whatever you switch to.

**4. A STAFF account without a branch is rejected.**
`UserServiceImpl` throws `400` if `role == STAFF` and `branchId == null`. Process Rule #5 scopes staff
queries by their branch — a staff account with no branch either sees nothing or sees everything, and
both are wrong. Making it unrepresentable is cheaper than handling it.

## `CurrentUser` — the foundation for Process Rule #5

```java
CurrentUser.id()                     // Optional<UUID>  — from the token subject
CurrentUser.role()                   // Optional<Role>
CurrentUser.branchId()               // Optional<UUID>  — empty for customers/admins
CurrentUser.isAdmin()                // boolean
CurrentUser.canAccessBranch(id)      // admin: any branch. staff: only their own.
```

Everything here comes from a token **this server signed**. A client cannot claim to be staff at a
branch they do not belong to, because they cannot forge the signature. That distinction — trusting the
token, never the request body — is the whole argument for why branch scoping actually holds.

## What I deliberately did NOT do

**Endpoint role rules.** I did not add `requestMatchers(...).hasRole("ADMIN")` to `SecurityConfig`.
Right now every authenticated user can hit every endpoint. Deciding who may touch what is a policy
question about how the spa actually operates, not something to guess while you are eating. Proposal for
when you are back:

| Endpoint | Who |
|---|---|
| `/api/v1/auth/**` | anyone |
| `/api/v1/users/**` | ADMIN only |
| `/api/v1/branches` POST/PUT/DELETE | ADMIN only |
| `/api/v1/branches` GET | any authenticated user |
| `/api/v1/massages` GET | any authenticated user |
| `/api/v1/massages` POST/PUT | ADMIN only |
| `/api/v1/forms/**` | CUSTOMER (own only), STAFF (own branch), ADMIN (all) |
| `/api/v1/patient-intake/**` | STAFF + ADMIN |

The `forms` row is the hard one and it needs query-level filtering, not just endpoint blocking. That is
0.6c.

**Per-query branch filtering.** `findByBranchId` exists on the therapist, room, and appointment
repositories, but nothing forces a staff member to pass *their own* branch ID yet. That is the actual
substance of Process Rule #5 and it touches several services — worth doing deliberately, with you.

## Cleanup worth doing

Your controllers each carry `@CrossOrigin(origins = "http://localhost:4200")`. `SecurityConfig` now has
a proper `CorsConfigurationSource` bean reading `FRONTEND_ORIGIN` from `.env`. Two sources of truth for
CORS is how you end up with mysterious browser errors in Sprint 1. Delete the annotations and let the
bean own it.
